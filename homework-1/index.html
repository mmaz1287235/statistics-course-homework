Elliptic Curve Cryptography and Blockchain

A small experiment with secp256k1, followed by a statistical look at its output and a comparison of cryptography across different blockchains.

1. Background

A cryptographic hash takes an input and returns a fixed-size result. In a well-designed hash, small changes to the input should produce very different outputs. Elliptic curve cryptography (ECC) is something else: it works with points on a curve and is commonly used for public-key cryptography and digital signatures.

Here we use the elliptic curve secp256k1, defined over a finite field by y² = x³ + 7 (mod p). It has a standard base point G and a group order n. For a scalar k, we compute the point P = kG.

To make a toy “hash”, I first convert the UTF-8 bytes of the input into a scalar using a simple rolling calculation modulo n. I then multiply G by that scalar and return the 256-bit x-coordinate of the resulting point. This gives a fixed-size output, but it is not a secure hash construction. The rolling calculation has a predictable structure and can be attacked; using a real elliptic curve does not automatically make the result secure.

3. Statistical observations

I use a reproducible set of sample messages (sample-0000, sample-0001, and so on). For each message, the code flips one bit in the last UTF-8 byte and measures the Hamming distance between the two 256-bit outputs. It also measures overall bit balance, pooled binary entropy and repeated outputs.

Click the button to run the experiment.

How to read these results

Bit balance: For random-looking 256-bit outputs, approximately half of the bits should be 1. With a small sample, we should not expect exactly 50%.

Avalanche effect: A strong hash is expected to change roughly half the output bits when just one input bit changes. We report the observed Hamming distance, not a proof that the avalanche property holds.

Entropy: The reported number is the binary Shannon entropy calculated from the pooled proportion of zeros and ones. It describes bit balance only; it does not measure the cryptographic entropy or unpredictability of the output.

Collisions: Not finding repeated outputs in this small set is weak evidence. The rolling conversion of text into a scalar is not collision-resistant, and reducing modulo the curve order can create collisions. Different points can also share an x-coordinate (P and −P).

Method and limitations

The experiment is deterministic, so anyone running the same sample size obtains the same figures. The 50% bit balance and 128/256 changed bits are useful reference values, not formal acceptance thresholds. The sample messages are similar rather than randomly selected, and this is not a complete randomness test suite. I also do not test resistance to preimages, second preimages or carefully constructed collisions. A few good-looking statistics cannot establish these properties.

The biggest weakness is the first step: converting bytes into a scalar by repeatedly multiplying by 257. For short inputs this encoding is predictable and, without modular wraparound, easy to reconstruct from the scalar. Multiplication by the real secp256k1 base point does not turn that simple encoding into a standard secure hash function. It is only an illustration of how message data can be mapped into a curve computation.

4. Research: cryptography and statistics in blockchains

The three examples below show that blockchains use cryptography for different purposes: linking data, proving authorization and reaching agreement on the ledger. Their statistical questions are different too.

Bitcoin

Bitcoin uses SHA-256 in block headers and proof of work. Miners repeatedly change parts of a candidate block until the hash falls below a target. Each trial can be modeled approximately as a Bernoulli trial with a very small success probability, so the number of attempts needed is random. A lower target means finding a valid block is harder.

For a simple probability model, let p be the probability that one independent hash attempt meets the target. The number N of trials until the first success follows a geometric distribution: Pr(N = k) = (1 − p)^(k − 1) p, for k = 1, 2, .... Its expected value is E[N] = 1/p. For example, if p = 1/1,000,000, we expect one million attempts on average, but that is not a guarantee of success after one million tries. This helps explain why mining times vary.

For spending coins, signatures prove authorization. Bitcoin has used ECDSA over secp256k1 for years; Taproot also supports BIP340 Schnorr signatures over the same curve. The hash function and the signature algorithm do different jobs: hashing commits to data, while signatures prove that a valid key authorized a transaction.

Ethereum

Ethereum uses Keccak-256 for addresses and data structures such as transaction-related hashes. Normal externally owned accounts use ECDSA with secp256k1 to sign transactions. Ethereum does not use Bitcoin-style mining anymore: under proof of stake, validators are selected to propose blocks and participate in committees. Random selection and stake weighting introduce probability into the consensus process, while penalties help discourage dishonest behavior.

This is a useful difference from Bitcoin. Both networks use related public-key cryptography for user accounts, but their methods for agreeing on new blocks are quite different.

There is a probability question here as well. In a simplified model, if a validator controls a fraction w of the total effective stake, its chance of being chosen as a block proposer in a given slot is approximately w. Over T comparable slots, the expected number of proposals is approximately T × w. Real Ethereum selection follows a protocol-defined pseudorandom process, so this model is an illustration rather than a full simulation of the protocol.

Solana

Solana transactions normally use Ed25519 signatures, based on a different curve from secp256k1. Solana also uses Proof of History: a sequence of repeated cryptographic hash computations helps provide a verifiable ordering of events. Proof of History is not, by itself, the entire consensus mechanism; the network also relies on stake-based validator participation.

The statistical link here is less about mining trials and more about validator behavior, network performance and the assumptions behind cryptographic hash outputs.

Proof of History repeatedly applies SHA-256 so that later values depend on earlier ones. This is different from my secp256k1 toy output, which maps each input to a curve point. Both involve deterministic calculations, but they do not provide the same security guarantees. Looking at bit frequencies or Hamming distances may be interesting in either case, while neither test proves that the system is secure or that its consensus rules work correctly.

What statistics adds

The most direct statistical example is Bitcoin mining: a very small success probability repeated many times explains why block discovery is irregular. In proof-of-stake networks, random committee or proposer selection creates different probability questions. Statistics can also help monitor transaction activity and unusual patterns, though that kind of analysis is separate from the cryptographic proof that a signature is valid.

Overall, cryptography provides mathematical mechanisms for integrity and authorization. Statistical analysis helps us describe randomness and observe behavior, but a few experimental tests cannot prove that a cryptographic system is secure.
