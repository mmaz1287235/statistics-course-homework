MSC CYBERSECURITY · STATISTICS 2026/2027

From wallet seed to Ethereum address

How mnemonic words, hierarchical derivation, elliptic curve multiplication and hashing produce an Ethereum address. The page uses a published test phrase and explores the statistical properties of the relevant operations.

Educational demonstration. This page uses public test data only. The JavaScript elliptic curve implementation is intended for verification and explanation, not for holding funds or processing real wallet secrets. Do not enter your own recovery phrase anywhere on this page.
01

Wallet pipeline

Each operation has a separate purpose.

INPUT

Mnemonic words

BIP-39 represents encoded entropy and checksum bits as words from a fixed list.

BIP-39

Binary seed

PBKDF2 with HMAC-SHA512, 2048 iterations, turns the mnemonic and optional passphrase into a 64 byte seed.

BIP-32 / BIP-44

Private key

HMAC-SHA512 initializes the key tree. A standard path selects an Ethereum account key.

secp256k1

Public key

Scalar multiplication computes Q = kG on the secp256k1 curve.

Keccak-256

Ethereum address

Hash the 64 public key coordinate bytes and keep the rightmost 20 bytes.

EIP-55

Checksum case

Selected hexadecimal letters become uppercase to help identify typing errors. The address bytes do not change.

What these terms mean

Generation

Creating new secret entropy, usually with a secure random source. This demo does not generate wallet secrets.

Derivation

Computing related keys deterministically from a seed and a path.

Public key cryptography

Relating a secret scalar to a public curve point. Ethereum uses signatures for transaction authorization.

Hashing

Mapping data to a fixed length digest. It is not encryption.

Checksum

Adding redundancy to detect some mistakes, not to provide authentication.

Encoding

Representing binary values as words or characters without adding secrecy.

03

Statistical exploration

Theoretical quantities and measurements from controlled inputs.

Mnemonic entropy and checksum

BIP-39 adds ENT/32 checksum bits to entropy of length ENT, then divides the result into groups of 11 bits. The checksum detects many invalid phrases, but it does not add secret entropy.

WordsEntropy (bits)Checksum (bits)Total (bits)

The number of candidate word sequences is 2 raised to (11 × word count); the number with a valid checksum is 2 raised to ENT. This assumes uniformly selected entropy.

Keccak-256 and SHA3-256 use different domain separation. SHA-512 belongs to SHA-2. Their digest lengths also differ, so comparisons use the fraction of changed output bits.

EIP-55 error detection

Start from an official EIP-55 example. Change one random hexadecimal character while keeping it hexadecimal, then check whether the new mixed case text matches the EIP-55 encoding. Results depend on the chosen mutations. The official EIP-55 specification reports a 0.0247% average false positive rate for its address case scheme, which is not a prediction for this particular test.

No measurements yet.

The experiment tests single character substitutions, not every possible error. An EIP-55 checksum is probabilistic error detection and offers no protection against intentional address substitution.

How to interpret the observations

A well designed hash should change roughly half its output bits when an input bit changes, but a small experiment cannot prove preimage resistance or collision resistance. The sample mean and its spread describe only the selected inputs. EIP-55 is a check on the written representation, rather than the entropy or security of the underlying private key. A mnemonic chosen by a person is not guaranteed to have the theoretical entropy of a randomly generated BIP-39 mnemonic.

04

Cryptographic discussion

Different tools solve different problems.

Why not one algorithm?

BIP-39 makes wallet recovery manageable and derives the binary seed. BIP-32 creates a tree of keys from it, while BIP-44 standardizes which branches applications use. Neither replaces elliptic curve cryptography. secp256k1 supplies public keys and supports the signatures needed to authorize transactions. Keccak-256 condenses the public key to the data from which Ethereum takes its address. EIP-55 adds error detection to its written form.

SHA-512 versus Keccak and SHA-3

SHA-512 is part of the SHA-2 family standardized in 2001 and is used inside HMAC and PBKDF2 in this pipeline. SHA-3 was standardized in 2015 from the Keccak design, but its padding and domain separation are not the same as Ethereum's Keccak-256. As a result, Keccak-256 and SHA3-256 return different digests for identical messages. Substituting SHA3-256 during Ethereum address derivation produces a different address.

Historical context

  1. 1977: RSA. Early public key cryptography.
  2. 2001: SHA-2. NIST publishes the family including SHA-512.
  3. 2012: BIP-32. Hierarchical deterministic key trees.
  4. 2013: BIP-39. Mnemonic sentences for deterministic wallets.
  5. 2014: BIP-44. Shared structure for account paths.
  6. 2015: SHA-3. NIST standardizes a Keccak based hash family.
  7. 2016: EIP-55. Mixed case Ethereum address checksums.

Dates indicate the approximate introduction or standardization requested in the assignment, not universal wallet adoption.

What wallet software does

Applications such as MetaMask and Rabby expose account addresses and recovery workflows. They normally hide most intermediate seed and key calculations. A new wallet typically generates recovery words, while importing a recovery phrase reconstructs accounts using derivation paths. This page demonstrates the underlying mathematics but does not reproduce the wallet interface. A recovery phrase grants control over the wallet and must not be typed into an untrusted demonstration. No real wallet was connected for this assignment.
